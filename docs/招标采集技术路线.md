```

```

### 0.3 三条铁律（违反就会出 §6 里那类 bug）

1. **`upsert()` 是"整行覆盖"，不是"打补丁"**。传半个 row 进去，没传的列会被写成 NULL（§6-B1，已在生产数据里发生）。
2. **`ensure_table()` 每批调一次就够**，绝不要在每条记录前调。里面的 ALTER 一旦失败会 rollback 掉整批已 UPDATE 的记录（`tender.py:284` 的注释就是这场事故）。
3. **去重命中后不要改 `source`**。dedupe 只该改 `doc_uid`，否则源归属被来方覆盖（§6-B4）。

## 2. 逐源详解

## 2.1 cebpub —— 中国招标投标公共服务平台（主力）

**方案：API 直调，不碰验证码。**

### 为什么是它
按《电子招标投标办法》，所有招标公告都必须同步到这个平台。所以它覆盖的是**全部企业招标平台**（中国海油、甘肃智慧阳光、安徽省能源集团、中国招标采购云中心…），比任何第三方聚合站都全。实测搜「税务」有 497 条有效期内公告。

### 怎么绕过验证码 —— 不绕，走它自己的「首次免验证」
页面 JS（`jiaoyigongkai_shuakuai.js`）里写着：

```js
if (isFirstQuery) { isFirstQuery = false; executeBusinessQuery(); }  // 免验证
else { withVerification(...) }                                       // 要 vaptcha
```

`isFirstQuery` 是**页面级变量**，所以只要新开一个浏览器实例，第一次查询就免验证。代价是每次查询付一次浏览器启动（15-20 秒），换来**无额度限制、无验证码破解**。

关键调用：直接执行页面内部的 `performSearchRequest(null)` —— 复用它自己的请求构造，参数一个都不用猜。

### 现在走的是「更快的那条」：直调 API
浏览器路径（`_search_async`）保留但**`collect()` 已不用它**。直调 `getStringMethod.do` 比浏览器**快 100 倍**（0.1 秒 vs 20 秒），代价是只能拿第 1 页 —— 而翻页在服务端要 vaptcha token。

于是用**「地区 × 关键词」覆盖**：每个组合都是一次独立的第 1 页查询。

```
20 个关键词 × 31 个省级地区（+1 次全国）= 640 次查询 ≈ 1-2 分钟
```

### 踩过的坑（都是注释里记着的）

| 坑 | 现象 | 结论 |
|---|---|---|
| `searchArea` 必须 6 位编码 | 传中文「北京市」→ 服务端忽略该条件，返回全国 498 条；传 `110000` → 61 条北京 | **地区遍历能不能生效全靠这个**（`AREA_CODES` 表） |
| 参数缺一个就 0 条 | `searchIndustry=`、`centerPlat=` 这类空字段**也必须出现在 body 里** | 2026-10-22 调了半天返回 0 条的根因 |
| 发布时间字段名 | 用 `bulletinIssnTime` 时 78% 条目 `publish_at` 为空；真实字段是 **`receiveTime`** | 2026-10-23 修正（但仍残留 178 条空值，见 §6-B5） |
| 详情页要验证码 | `showDetails` 走的是 `withVerification`，不是「首次免验证」 | 采购人只能**从标题正则推断**（`_PURCHASER_RE`），认不出就显示「—」 |
| 频控 | 连续几百次后返回非 JSON（空/拦截页），实测 **640 次后被拦** | `api_search` 对非 JSON 做 1.5s×(n+1) 退避重试；调用方 `sleep_between=0.5` |

### 字段映射（`to_tender_row`）
- `title` ← `bulletinName` → `title` → `businessObjectName`（三级兜底）
- `region` ← 请求参数对应的中文名 ← `regionName`
- `agency` ← `transactionPlatfName`（**是"交易平台名"，被塞进"代理机构"列**，页面标签会误导）
- `deadline` ← `bulletinEndTime`（**是"公告结束时间"，不等于投标截止**，邮件剩余天数据此算会偏）
- `purchaser` ← 标题启发式；`is_tax` 恒 1；`tax_hits` 恒 `["税务服务"]`
- **拿到却被丢掉**：`businessId`、`schemaVersion`、`tenderProjectCode`、`transactionPlatfCode`（§6-B6）

## 2.2 zlbx —— 知了标讯（企业税务标的主要来源）

**方案：付费 JSON API + `X-API-Key`。**

### 为什么换到这个源
CCGP 实测 400 条标题里 **0 条税务服务标** —— 它是政府采购网，主体是设备/工程。税务服务采购的买方是企业（国企/上市公司），标发在企业招投标平台。知了标讯用「税务服务/税务咨询/汇算清缴/涉税服务」搜到 **32764 条**，返回的全是真标（雅砻江水电税务咨询、新疆农牧投涉税服务选聘、惠州天然气汇算清缴鉴证…）。

### 认证与注册
```http
POST https://ai.zhiliaobiaoxun.com/web-api/internal/auto-register
{"device_features": {hostname, platform, arch, username, home_path, mac_hash},
 "agent_kind": "claude-code", "agent_version": "1.0.0", "skill_version": "tender-search/1.0"}
```
新设备送 **100 次免费调用**（绑定手机号再送 100）。Key 保存到 `data/zlbx_key.txt`（已 gitignore）；读取顺序：`ZLBX_API_KEY` 环境变量 → 文件 → 自动注册。

### 额度意识（这是设计约束，不是建议）
- `search_bids` 一次最多返 50 条，**每次翻页扣 1 次**
- 默认 `max_pages=2` → 100 条/轮；`days=7`
- 每天增量只抓最近 1-2 天 → 1-2 次调用/天，够用一两个月
- `get_bid_detail` **每次也扣 1 次**，所以 `fetch_details` 只补 `detail_fetched_at IS NULL` 的，且**每条即时 commit**（额度按次消耗，进程被杀不能丢成果）

### 详情能拿到什么（`get_bid_detail`）
| 返回字段 | 落到哪 | 备注 |
|---|---|---|
| `source`（HTML） | `source_html`（经 `html_to_text`） | 正文 |
| `source_url` / `url` | `source_url` | 原文链接，多为 `ctbpsp.com` 详情页 |
| `caller_contact` / `agency_contact` | `contact_phone` | **部分打码**（如 `057*****6187`），平台对匿名用户脱敏 |
| `caller_person` / `agency_person` | `contact_person` | — |
| `signup_time` / `tender_time` | `signup_time` / `tender_time` | 报名/开标时间 |
| `pub_time` / `caller_name` / `agency_name` | `publish_at` / `purchaser` / `agency` | 顺手校正列表值 |

### 踩过的坑
- **去重判定顺序**：必须先看「自己是否已存在」，**只有自己不存在时**才 `find_duplicate`。反过来写会把"已存在条目自己的更新"重定向到另一条重复记录上，导致原记录的字段（如 `bid_process`）永远补不上（2026-10-22 踩到）。
- 知了聚合多平台，**同一公告重复收录**（`bid_id` 不同、标题日期完全相同），实测 100 条里 6 组。
- `deadline` **从来没被写入**（列表无此字段，详情有 `tender_time` 但没回填）→ 邮件提醒永远不含 zlbx（§6-B3）。

## 2.3 ccgp —— 中国政府采购网（已弃用）

**方案：浏览器渲染（直连 403）。**

### 站点特征（2026-10-21 实测）
- 列表 `https://www.ccgp.gov.cn/cggg/{zygg|dfgg}/index_N.htm`，各 20 条/页，静态分页可用
- 条目链接 `./gkzb/202610/t20261021_27538088.htm`（`gkzb` 公开招标 / `zbgg` 中标 / `gzgg` 更正 / `cjgg` 成交 / `qtgg` 其他）
- **反爬**：直接 HTTP 请求返回 **403**，必须走真浏览器
- 详情页是表格结构，含项目编号/项目名称/预算/采购单位/截止时间

### 抓取策略：标题全量、详情按需
CCGP 每天新增数千条，全抓详情（一条 3-5 秒浏览器）要数小时。折中：
- **所有列表条目都入库**（标题、类型、日期、URL、`is_tax`）
- **只有命中税务关键词的才抓详情**
- 其余给"查看原文"直接跳 CCGP

这样每天约 6 分钟跑完（列表 50 页 + 详情 20-30 条）。

### 为什么弃用
技术是通的，但**命中率太低**：400 条标题 0 条税务服务标。现在只在 `--source ccgp` 手动指定时运行，`cli.py` 的 `max_pages` 会被强制抬到 ≥60。

### 坑
- `_region_from_title` 用 48 条硬编码城市→省份映射从标题猜地区，猜不出留空
- 停页依据是"该页最老条目早于 cutoff"，`strptime` 失败就静默继续

## 2.4 cms_platform —— 通用 CMS 采集器（邮储 / 湖北联投）

**方案：静态 JSON 列表 API + 静态 HTML 详情页。一套代码覆盖多个同款 CMS 平台。**

### 为什么这个模块价值最大
2026-10-23 实测发现：**湖北联投电子采购平台**和**中国邮政储蓄银行邮银易采平台**用的是同一个 CMS（`/cms/api/dynamicData/queryContentPage` + `/cms/default/webfile/` 详情页）。也就是说「适配一次 = 覆盖一批平台」，不用为每个平台从头逆向。

### 两条链路（都实测通过）
```http
POST {base}/cms/api/dynamicData/queryContentPage
{"pageSize":"20","pageNo":"1",
 "dto":{"siteId":"725","categoryId":"221","city":"","county":"","purchaseMode":""}}
→ {"res":{"total":256,"rows":[{title, url, contentId, publishDate,
                               quoteBeginTime, quoteEndTime,
                               agentCompanyName, provinceName, ...}]}}

GET {base}/cms/default/webfile{url}     # url 是列表返回的相对路径
```
**详情链接少 `/cms/default/webfile` 前缀会 404** —— 这是最容易犯的错。

### 栏目配置（只配**可投标**的栏目）
| 平台 | `base` | `siteId` | 收的栏目 | 不收的 |
|---|---|---|---|---|
| 湖北联投 `ltzxgl` | `https://www.ltzxgl.com.cn` | 725 | 221 招标公告（256）、225 采购公告（14983）、227 变更公告（1201） | 222/223/226（中标/候选人/结果） |
| 邮储 `psbc` | `https://cg.psbc.com` | 725 | 223 公开招标（10022）、226 其他采购（2263） | — |

> 两个平台的 `siteId` 都是 725 —— **siteId 是站内编号，不是全局 ID**，别以为是同一个站点。

### 坑
1. **`title` 搜索参数无效**：传「税务」返回 0 条 → 只能**全量翻页 + 本地关键词过滤**（每个栏目几百条，翻十几页；实测 428 页 / 8520 条 / 匹配 67 条，耗时 1530 秒）。
2. **平台客服电话污染**：湖北联投每条公告页脚都有 `4001276998`，第一版把它当成了项目联系人。现在 `_pick_contact` 会：优先取「联系人：X」后 160 字内的号码；否则取全文；最后**排除所有 400 开头**的号码（`_PLATFORM_SERVICE_PHONES` 记录已知客服号）。
3. **`_strip()` 正则有个多余的 `}`**（`cms_platform.py:71`）：`</(?:p|div|tr|li|h\d)}>` —— `}` 是字面量，永远匹配不到，所以块级换行从未插入，正文粘成一整段（§6-B9）。
4. `notice_type` 恒为 `gkzb`、`bid_process` 恒为 `招标`，**栏目名没落库** → 变更公告也被标成"招标公告"。
5. `purchaser` 取的是 `agentCompanyName`（字段语义更接近"代理/招标单位"），与 `agency`（平台名）容易混。

## 2.5 csg —— 南方电网

**方案：纯静态 HTML，不用浏览器、不用 API 逆向。**

### 站点特征（2026-10-23 实测）
- 列表 `https://www.bidding.csg.cn/{zbgg|zbcg|fzbgg}/index.jhtml`，分页 `index_N.jhtml`
  - `zbgg` 招标公告（35 条/页，2288 页）、`zbcg` 采购公告、`fzbgg` 非招标公告
- 详情 `/{栏目}/{id}.jhtml`，正文 6000+ 字符，含招标人/截止/开标/地址

### 为什么这个平台特别有价值
南方电网的招标公告里有大量「税务咨询/涉税服务/汇算清缴」类采购（电网企业每年都要选聘税务服务中介），而且**完全公开可抓** —— 比央企自建 SPA 平台省事得多。

### 坑
- **电话号码正则必须收紧**：第一版把项目编号 `000062002311896` 抓成了电话。现在要求「区号第 2 位不能是 0」+ 词边界 `\b`（§`_PHONE_RE` 注释）。
- `publish_at` 依赖正文里的「发布时间：YYYY-MM-DD」，没有就留空。
- 详情页里**没有解析采购人**，`purchaser` 恒 NULL（4 条数据全空）。
- 只按标题关键词过滤 → "中介机构选聘"这类不含"税务"的标题会漏。

## 2.6 detail_fetch —— 通用详情补全（浏览器渲染）

**方案：真浏览器打开 `source_url` → 全文文本 → 取最长连续文本块当正文 → 正则抽联系方式。**

### 为什么要「通用」这一层
招标公告分散在 **124 个原始平台**（邮储、中国海油、甘肃智慧阳光、各央企自建平台…），逐个写适配器成本极高。但它们有共性：`source_url` 指向发布方详情页。所以先做一层通用的，能覆盖一批，剩下的再单独适配。

### 为什么要浏览器
实测 69 条 `source_url` 里只有 **37% 能直抓**：其余是 SPA（`#/` 路由，HTML 里没有内容）、反爬 406、502。浏览器渲染能解决 SPA 这一类。

### 提取策略（不依赖 DOM）
1. 渲染后取全文文本
2. **找最长的一段连续文本块**当正文（导航/页脚通常短而碎）
3. 正则抽电话、邮箱、联系人、日期 —— 这些格式全国通用

`extract_body` 的判定：跳过空行、跳过 `_NOISE_PAT`（首页/登录/版权所有…）、跳过长度 ≤2 的行，累计长度最大者为正文；不足 `min_len=200` 时退化为全文。

### 现状：**代码在，没人调**
`fetch_all_pending()` 只处理 `source_url` 非空且 `source_html` 为空的行。但：
- **cebpub 的 505 条 `source_url` 全是 NULL**（因为 `to_tender_row` 丢了 `businessId`），这条链路对主力源完全无效
- 没有任何 CLI / 调度调用它
- 它还会用 `doc_uid` 前缀猜 `source`（`cebpub` if not `zlbx:`），对 `cms:` / `csg:` 会**写错源**（§6-B11）

## 2.7 browser.py —— 浏览器底座

**方案：Playwright（同步/异步）+ nodriver 双栈。**

### 为什么需要它（原本是为政策库写的，招标复用）
实测六个省对普通 HTTP 请求返回 412，响应体是**加速乐（Jiasule）WAF 的 JS 挑战**：

```
山东 server: wswaf   <script>$_ss=window['$_ss'];$_ss.ssd=100343;...
北京 server: ******   <script>$_ts=window['$_ts'];$_ts.nsd=109776;...
湖南 server: core     <script src="/MMB1_.../ZYbKRgIknL7izCT.js"> + set-cookie
```

机制：首次请求返回 412 + 一段 JS → 浏览器执行 JS 算出 cookie → 带 cookie 重试才放行。所以**换请求头无效**（实测三种组合结果一致），`curl_cffi` 能过纯 TLS 指纹检测但过不了要执行 JS 的。

**不走「逆向 WAF 的 JS」那条路**：GitHub 上确有 jiasule 类仓库，但 ① 脆弱（WAF 一更新就失效）；② 属绕过安全机制的灰色地带。用浏览器则是以正常用户的方式访问公开信息。

### 关键设计
| 设计 | 原因 |
|---|---|
| `_IGNORE_TLS = True` | 河北、青海税局证书与域名不匹配（`ERR_CERT_COMMON_NAME_INVALID`），浏览器直接拒绝导航；这两站曾被误判成"抓不到" |
| 自定义 UA | Playwright 默认 UA 带 `HeadlessChrome`，会被识别 |
| `--disable-blink-features=AutomationControlled` | 默认 headless 特征会触发挑战死循环，正常用户反而进不去 |
| `fetch_many` 按域名复用 context | 加速乐 cookie 是**按域名**的 → 挑战每域名只过一次；267 条省级详情从 40 分钟降到 3 分钟 |
| 每层 `asyncio.wait_for` 超时 | 没有它，一个连不上的域名会让整批无限挂住（实测卡死 15 分钟一条没落库） |
| 首条失败重试 `wait_ms*3` | 有的站要 12 秒以上（辽宁） |
| 同域其余页失败重试「超时翻倍」 | 广东几条问答页 25 秒不够，直接记失败太可惜 |
| nodriver 兜底 | 西藏税局 Playwright 只返回 39 字节空壳，nodriver 拿到 50009 字节；两栈反检测强度不同，覆盖面不重合 |

`_find_browser_binary()` 复用 Playwright 已下载的 Chromium（`%LOCALAPPDATA%\ms-playwright\chromium-*\chrome.exe`），不必再下 150MB。

### 3.2 `doc_uid` 生成规则（**改这里前先读 §6-B4/B5**）

| 源 | 格式 | 稳定性 |
|---|---|---|
| cebpub | `cebpub:<sha1(title\|platform\|publish_at)[:16]>` | ❌ **不稳**：字段一变就是新 id |
| zlbx | `zlbx:<bid_id>` | ✅ |
| ccgp | `ccgp_zygg:<url 里的数字 id>` | ✅ |
| cms | `cms:<platform_key>:<contentId>` | ✅（注意前缀是 `cms:`，source 是 `cms_xxx`，**不是数据损坏**） |
| csg | `csg:<url basename 去掉 .jhtml>` | ✅ |

### 3.3 去重三道闸

1. **`doc_uid` 主键**（`upsert` 按它幂等更新）
2. **`find_duplicate()`**：先精确匹配 `title + purchaser`，再忽略「开头 1-2 位数字」比较规范化标题
   - `_normalize_title` 只去 **1-2 位**数字：知了会把同一公告收录成「10中国建设银行…」/「7中国建设银行…」；4 位通常是年份（"2026年度企业所得税…"），去掉会把不同年份混成一类
3. **同批内先查自己**：`self_exists` 为真时**不再**走 `find_duplicate`（顺序写反会导致更新被重定向，见 §2.2）

**已知漏网**：采购人字符串跨源不一致时（「安徽省分行」 vs 「中国邮政储蓄银行股份有限公司」）标题去重失效 → 同一条标在库里 3 份（`cebpub` + `cms_psbc` + `zlbx`）。邮件 (`notice.py`) 按标题去重兜底，**列表页不去重**。

### 3.4 税务判定（`tender.py`）

分两级，**先强后弱**：

```python
STRONG_KEYWORDS:  税务咨询/税务代理/涉税鉴证/汇算清缴/转让定价/税务尽调/税审 …
WEAK_KEYWORDS:    税务/涉税/纳税/税收/发票/增值税/企业所得税 …
SERVICE_FORM_WORDS: 服务/咨询/代理/鉴证/审计/筹划/顾问/外包/委托/尽调/检查/评估 …
```

1. 命中**强关键词** → 直接认定
2. 只有弱关键词 → **先剔除采购人名称**（`国家税务总局|税务局|税务部门|税务系统`…），再看剩余文本有没有交付形态词

**为什么**：2026-10-21 实测，只用一张宽表会把「国家税务总局云南省税务局网络及安全等设备维保服务项目」标成税务服务 —— "税务"命中的是**采购人名称**，不是采购内容。那类条目对投标毫无意义，纯噪音。

CCGP 每天新增数千条，靠这个本地过滤先筛再抓详情，**省 95% 的抓取时间**。

> 注意：cebpub 与 zlbx 的 `is_tax` **恒为 1**（搜索词本身就是税务领域），不走上面的判定。真正的误报过滤交给 AI（§3.6）。

### 3.5 「还能投」判定（`bid_process`）

```
可投：招标 / 预招标 / 采购意向      （BIDDABLE_PROCESSES）
已结束：中标结果 / 中标候选人 / 合同  （FINISHED_PROCESSES）
```
`is_biddable()` 的原则：**未知阶段一律当真**（宁可多显示，不要误杀）。
页面与邮件都用 SQL 硬编码 `bid_process NOT IN ('中标结果','中标候选人','合同')`（NULL 视为可投）。
`cms` 另外在标题层过滤 `_FINISHED_WORDS`（中标候选人/成交结果/废标/流标/终止公告…）。

### 3.6 AI 推荐度（`tender_ai.py`）

**为什么需要**：税务关键词会误抓「国家税务总局荆州市沙市区税务局**食堂服务**采购项目」—— 有"税务局"有"服务"，买的是食堂承包。

模型做三件事：① 鉴别真伪 ② 看采购人（企业/银行 > 政府机关）③ 看截止日还剩几天。

| 分 | 含义 |
|---|---|
| 5 | 明确税务专业服务 + 企业/银行采购 + 时间充足 |
| 4 | 税务专业服务，采购人一般或时间紧 |
| 3 | 沾边不核心（"财务+税务"打包、税务培训） |
| 2 | 只是采购方是税务单位，买的不是税务服务 |
| 1 | 非税务服务，或已截止 |

**三类最容易误判的**（写进 prompt 了）：标题含"税务局"≠税务服务；软件/系统开发/信息化**不是**税务服务（≤2 分）；工程/货物/监理/维修/租赁/物业（≤2 分）。

- 模型：`qwen3.8:27b-ud-q3` @ `http://127.0.0.1:11434/api/generate`（**注意：文件头注释说用 14B、27B 太慢，代码实际是 27B**，§6-B14）
- `"think": False` —— Qwen3 **必须关思考**，否则输出预算被推理吃光、返回空
- 只输出一行 JSON：`{"score":1-5,"is_tax_service":bool,"reason":"≤20字"}`
- `judge_pending` 只处理 `is_tax=1 AND ai_score IS NULL`，每条 commit（跑 1-2 小时的任务，杀进程不丢成果）
- 解析失败 → `score=0` → 记 `failed`、**不写库**（下轮重试）

### 3.7 页面可见性口径（`web/tender_routes.py`）

`GET /tenders` 参数与默认值：

| 参数 | 默认 | 作用 | 注意 |
|---|---|---|---|
| `tax_only` | `1` | `is_tax=1` | **UI 取消勾选无效**（缺参仍按 1 处理，§6-B8） |
| `ai_only` | `1` | 排除 `ai_is_tax_service=0`；**NULL 保留**（宁多勿漏） | **UI 无此开关**，只能改 URL |
| `show_finished` | `0` | 是否含中标/合同 | — |
| `recent` | `90` | 近 N 天发布 **且未截止**；截止日未知**保留** | CMS 平台历史标多，不滤第一屏全是过期标 |
| `days` | `30` | 又一个"近 N 天发布"过滤 | **与 `recent` 语义重复**，两个都生效 |
| `q` / `region` / `notice_type` | 空 | 标题/正文/项目编号模糊、地区、类型 | — |
| `page` / `limit` | 1 / 30 | 分页（`limit ≤ 100`） | — |

页面附加计算：`days_left`、`urgent`（≤3 天标红）、筛选项从库里 `DISTINCT` 现取（不维护硬编码列表）。
详情页 `/tender/{doc_uid}`：优先显示 `source_html`，其次 `content`，都没有则提示"只抓到列表级信息"。

## 5. 运维命令速查

> 统一前缀：`.venv\Scripts\python.exe -m taxassist`（下文简写 `taxassist`）。
> **Windows 铁律**：中文不要经 shell 传给 Python/psql（CP936 会乱码），参数一律用 ASCII。

### 5.1 采集

| 命令 | 用途 | 备注 |
|---|---|---|
| `taxassist tenders` | 默认跑 **cebpub**（地区×关键词 640 次） | ⚠ 当前会在汇总打印处抛 `KeyError: 'keywords'`（§6-B2）；数据已提交，可忽略 traceback |
| `taxassist tenders --source zlbx --days 7 --max-pages 2` | 知了标讯，7 天内、2 页（100 条，扣 2 次额度） | `--max-pages` 每页 = 1 次额度 |
| `taxassist tenders --source zlbx --source cebpub` | 多源顺序跑（可重复 `--source`） | choices 只有 `cebpub/zlbx/ccgp` |
| `taxassist tenders --source ccgp --detail-limit 5` | CCGP（已弃用），最多 5 条详情 | `max_pages` 会自动抬到 ≥60 |
| `taxassist tenders --source cebpub`（想只跑某几省） | ❌ 无参数，需改 `AREA_CODES` 或在 Python 里传 `areas=` | 见 §5.6 片段 |

### 5.2 补详情

| 命令 | 用途 | 额度 |
|---|---|---|
| `taxassist tender-detail --limit 20` | zlbx **API** 补正文/原文/联系方式/时间（`detail_fetched_at IS NULL`） | **20 次** |
| `taxassist tender-detail` | 补全部待补 | 按条数扣 |

> `tender-detail` **只走 zlbx API**，不包含 `detail_fetch`（浏览器通用补全）——后者没有 CLI。

### 5.3 AI 评分

| 命令 | 用途 |
|---|---|
| `taxassist tender-ai` | 评估所有 `is_tax=1 AND ai_score IS NULL` 的条目（约 3-5 秒/条） |
| `taxassist tender-ai --limit 50` | 只评 50 条（先小批量验证 prompt） |

跑之前确认 Ollama 在跑：`curl http://127.0.0.1:11434/api/tags`（或双击 `启动Ollama.bat`）。

### 5.4 邮件提醒

| 命令 | 用途 |
|---|---|

### 5.5 服务与调度

| 命令 | 用途 |
|---|---|
| `taxassist serve` | 起网站（默认 8765，含后台调度） |

### 5.6 未接线模块的手工跑法

`cms` / `csg` / `detail_fetch` 没有 CLI。在项目根目录建一个临时脚本（**不要用 `-c` 传中文**）：

```python

import sys
sys.path.insert(0, "src")
from taxassist import db
from taxassist import tender as tmod

conn = db.connect()

# ① CMS（邮储 + 湖北联投）：max_pages=120 约 25 分钟
print(cms_platform.collect(conn, max_pages=120, sleep_between=0.2))

# ② 南方电网：3 个栏目 × 30 页
print(csg.collect(conn, max_pages=30))

# ③ 通用详情补全（浏览器，10-20 秒/条，慎跑）
```

跑完记得核对：`SELECT source, COUNT(*) FROM tender GROUP BY source;`

### 5.7 数据库核查 SQL（PG）

```sql
-- 各源现状
SELECT source, COUNT(*) AS n,
       SUM(CASE WHEN source_html IS NOT NULL AND source_html <> '' THEN 1 ELSE 0 END) AS has_body,
       SUM(CASE WHEN deadline IS NULL OR deadline = '' THEN 1 ELSE 0 END) AS no_deadline
FROM tender GROUP BY source ORDER BY n DESC;

-- 未来 3 天到期的（= 邮件内容）
SELECT deadline, source, title FROM tender
WHERE is_tax = 1 AND deadline >= CURRENT_DATE AND deadline <= CURRENT_DATE + 3
  AND (ai_is_tax_service IS NULL OR ai_is_tax_service = 1)
ORDER BY deadline;

-- 检查 upsert 清空事故（有正文却没 notice_type）
SELECT COUNT(*) FROM tender WHERE source = 'zlbx' AND source_html IS NOT NULL
  AND notice_type IS NULL;

-- 检查 source 被去重改坏
SELECT split_part(doc_uid, ':', 1) AS uid_prefix, source, COUNT(*)
FROM tender GROUP BY 1, 2 HAVING split_part(doc_uid, ':', 1) <> source;
```

|---|---|

## 6. 已知 bug 与隐患

> 这一节是审计的**主要产出**。带 ✅ 的已在生产数据里得到验证（附证据与核查 SQL）。

### B1 ✅【高】`upsert()` 局部更新会**清空**未提供的列
`tender.py:298-316` 的 `fields` 把 `notice_type/bid_process/project_no/purchaser/agency/budget/region/publish_at/url/summary` 全部写死为 `row.get(...)`，没传就是 `None`。只有 7 个 detail 字段做了「带上了才写」的保护。

**后果**：`zlbx.fetch_details()` 和 `detail_fetch.fetch_all_pending()` 只传几个字段 → 把这些列的已有值全部抹成 NULL。
**证据**：68 条有正文的 zlbx 记录，`region/project_no/notice_type/url/summary/budget` **全部为 NULL**；同源 33 条**没补过详情**的记录里，这 6 个字段只有 1 条为空（就是 B4 里那条被去重改源的）。
**修法**（任一）：
```python
# A. 白名单化：只写 row 里确实出现的键
fields = {k: v for k, v in {...}.items() if k in row}
# B. detail 链路先 SELECT 原行，update 后再 upsert（合并语义）
# C. 用 SQL COALESCE(?, col) —— 但就无法把字段显式置空了
```
**验收**：补详情前后 `SELECT notice_type FROM tender WHERE doc_uid='zlbx:xxxx'` 不变。

### B2 ✅【高】`taxassist tenders` 默认源打印时抛 `KeyError: 'keywords'`
`cli.py:240` 用了 `st['keywords']`，而 `cebpub.collect()` 返回的键是 `queries/fetched/new/updated/duplicates/failed`，**没有 `keywords`**。
**后果**：采集全部跑完（640 次查询、数据已 commit），最后打印汇总时崩 → 退出码非 0，自动化/定时任务会当成失败；`失败` 计数也恒为 0（`api_search` 吞异常返回 `[]`，`stats['failed']` 从未 +1）。
**修法**：改成 `st['queries']`，并把 `api_search` 的失败计数传出来。

### B3 ✅【高】zlbx 没有 `deadline` → 邮件提醒永远不含它
`_rows_from_items` 不落 `deadline`（列表 API 没有该字段）；`fetch_details` 拿到 `tender_time` 却没回填 `deadline`。
**证据**：zlbx 101 条 **0 条**有 `deadline`，而其余 5 个源 573 条里 572 条都有（只有 1 条 cms 缺失）。
**后果**：`notice.due_tenders()` 硬性要求 `deadline` 非空 → **企业税务标（最该提醒的那类）一条都进不了邮件**。
**修法**：`fetch_details` 里 `"deadline": (data.get("tender_time") or "")[:10] or None`；注意 `tender_time` 是开标时间，与投标截止近似，可在邮件里注明。

### B4 ✅【中】去重重定向把 `source` 改成"来方"源
`zlbx.collect` / `cebpub.collect` / `cms_platform.collect` / `csg.collect` 都这么写：
```python
if dup: row["doc_uid"] = dup   # 只该改 uid
upsert(conn, row)              # 但 row["source"] 仍然是来方 → 覆盖原记录
```
**证据**：10 条 `zlbx:*` 记录的 `source` 是 `cebpub`；8 条 `cebpub:*` 记录的 `source` 是 `cms_ltzxgl`。
**后果**：① `zlbx.fetch_details` 的 `WHERE source='zlbx'` 漏掉这 10 条（详情永远补不上）；② 按源统计失真；③ 页面"数据来源"显示错。
**修法**：重定向时删掉 `row["source"]`（让 upsert 不写该列），或直接给 `upsert` 加"只更新指定列"的参数。

### B5 ✅【中】cebpub 的 `doc_uid` 由 `title|platform|publish_at` 哈希 → 字段抖动就产生重复行
`_doc_uid()` 把 `publish_at` 也算进指纹，而 `publish_at` 本身有空值（178/505）。
**证据**：cebpub 内**27 组同标题重复**，典型一对：「四川物资产业集团总公司专项税务咨询服务」→ `cebpub:8d88…`（`publish_at=2026-10-09`）与 `cebpub:eb58…`（`publish_at=NULL`），平台名、采购人、地区完全相同。
**后果**：重复入库；`find_duplicate` 靠 `title+purchaser` 兜底，但标题带编号前缀或采购人推断不同时仍会漏。
**修法**：用 `businessId` 当 uid（`api_search` 已经拿到了，见 B6）；或指纹去掉 `publish_at`。

### B6【中】cebpub 采集到 `business_id` 却丢弃 → 无法"查看原文"
`api_search` 明确注释「`businessId + schemaVersion` 是 showDetails 的必需项，存下来才能构造查看原文链接」，但 `to_tender_row()` 只映射了 13 个字段，`business_id/schema_version/project_code/platform_code` **全部没落库**。
**后果**：cebpub 505 条 `source_url` 全空、`project_no` 全空；页面只能显示"数据来源 cebpub"而不能跳原文；`detail_fetch` 对主力源完全无效。
**修法**：`to_tender_row` 加 `project_no=tenderProjectCode`，并把 `business_id` 存进 `url`（或新列），页面拼 showDetails 链接。

### B7【中】邮件 09:00 早于招标采集 09:30
`scheduler.py`：`_job_tenders` = `CronTrigger(hour=(hour+2)%24, minute=minute)`，默认 **09:30**；`_job_tender_notify` = 固定 **09:00**。而注释写的是"在日更和招标采集之后，数据已是最新"。
**后果**：邮件用的是**前一天**的标；新入库的当天标要等第二天才提醒，紧的标可能来不及。
**修法**：`notify` 改成 `minute+5`（09:35），或干脆排在 `_job_tenders` 末尾。

### B8 ✅【中】前端「只看税务服务类」取消勾选无效
`tenders.html` 的 checkbox 未勾选时**不发送该参数**，而 `tender_routes.py` 签名是 `tax_only: str = "1"` → 缺省仍是 1。
**后果**：用户永远关不掉税务过滤（`?tax_only=0` 才有效）；`ai_only` 则**根本没有 UI 开关**，只能手改 URL。
**修法**：checkbox 配一个同名 hidden `value="0"`，或在路由里把缺省改为 `""` 并显式判断。

### B9 ✅【中/低】`_strip()` 正则多了个 `}` → 正文段落从不换行
`cms_platform.py:71` 与 `csg.py:50`：
```python
re.sub(r"</(?:p|div|tr|li|h\d)}>", "\n", s)   # ← } 是字面量
```
实测该正则**永不匹配**（`'<p>a</p><div>b</div>'` 原样返回），而 `detail_fetch.py:50` / `zlbx.py:177` 的同一行是**正确**的（无 `}`）。
**后果**：cms/csg 的 `source_html` 段落粘成一整行，详情页 `pre-wrap` 显示成一大坨。
**修法**：删掉那个 `}`；已入库的 68 条 cms/csg 记录需重抓才会变好。

### B10 ✅【低】cebpub 的 `failed` 统计永远 0
`api_search` 内部 `except` 后返回 `[]`，`collect` 的 `stats["failed"]` 从不累加 → CLI 显示的"失败 0"不可信（被限流也看不出来）。

### B11【低】`detail_fetch` 用 uid 前缀猜 source，会写错源
```python
got["source"] = "cebpub" if not row["doc_uid"].startswith("zlbx:") else "zlbx"
```
对 `cms:psbc:*`、`csg:*` 会被标成 `cebpub`。目前因该模块未接线而未爆，但一旦接线就会污染源归属。

### B12【低】`budget REAL` 在 PG 是 float4，预算存"元"会丢精度
PG 的 `REAL` 是 4 字节浮点（约 7 位有效数字）。`_money()` 把"万元"乘成"元"，上亿预算（如 123,456,789）会变成 123,456,792。SQLite 无此问题。
**修法**：改成 `NUMERIC(16,2)`（SQLite 侧仍兼容），或统一以"万元"存储显示时再换算。

### B13【低】只有 cebpub 进了调度
`scheduler._job_tenders` 只 import `cebpub`。zlbx/cms/csg 全靠手工 → 页面数据"半自动"（§1.2）。

### B14 ✅【文档/代码漂移】`tender_ai` 注释说 14B，代码用 27B
文件头：「`qwen3:14b`（快、全驻显存）…用 27B 会让每条从 5 秒变 30 秒，不划算」；实际 `MODEL = "qwen3.8:27b-ud-q3"`。
实测日志：约 **3-4 秒/条**（27B 在这台机器上并不慢），所以**代码是对的、注释过期**。改注释即可。
（同类漂移：`cli.py:221` 注释说"默认走知了标讯"，代码 `sources = args.source or ["cebpub"]` 是 cebpub；`AI_READ_FIRST.md` 说"默认仍是 SQLite"，但 `repo/conn.py` 的 `DEFAULT_BACKEND = "pg"`。）

### B15【低】`project_no` 被当成"随手放 id"的列
zlbx 放 `bid_id`、cms 放 `contentId`、cebpub 空。`tender.py` 文档承诺的「列表页按 `project_no` 聚合成一条展示最新阶段」**并未实现**（`tender_routes.py` 没有任何聚合逻辑）。要么实现，要么改掉这句文档。

### B16【低】没有任何 tender 相关测试
`tests/` 里只有省级政策（`test_collect_provincial.py`）。`tax_hits`、`_normalize_title`、`upsert` 局部更新语义、`_money` 全是纯函数，极易补测。

### B17【低】`_normalize_title` 的副作用
`^[\s\d]{1,2}[.、,，\s]*` 会把「2026年度企业所得税汇算清缴」削成「26年度…」。目前两侧同规则所以不会误合并，但**打印/调试时看到的不是原值**；且 1-2 位的短前缀（如「5G…」）也会被吃掉。
